# Documentation Format Convention

**Date**: February 10, 2026
**Phase**: 14

---

## Overview

Maestro documentation is split into two independent pipelines with fundamentally different characteristics:

| | Pipeline 1: Metrics | Pipeline 2: Knowledge |
|--|---------------------|----------------------|
| **Nature** | Factual data, numbers, test results | Observations, patterns, synthesized insights |
| **Method** | Deterministic scripts, no LLM | LLM-powered analysis and synthesis |
| **Reliability** | 100% -- data is extracted, never generated | Depends on LLM quality; guarded by confidence levels |
| **Maintenance** | Append-only (new data = new entry) | Living documents (revised, consolidated, deprecated) |
| **Failure mode** | Cannot fail (pure file I/O) | Can fail if LLM provider is down -- fails visibly, no silent degradation |
| **Cost** | Zero LLM cost | LLM inference cost per generation |

Pipeline 2 reads from Pipeline 1 output but never the reverse. If Pipeline 2 is unavailable, Pipeline 1 continues to function independently.

**Phase 14 constraint**: All documentation features are exposed via CLI and TUI Monitor only. No frontend React changes in this phase.

```

    docs/                              <-- Shipped with the app (git-versioned)
      models/                          <-- Model documentation (seed data)

      guides/                          <-- Usage guides
        getting-started.md

  user/
    docs/                              <-- Generated by usage (per-user, not versioned)
      metrics/                         <-- Pipeline 1 output
        sessions/
          {session-id}/

            report.md
            per-phase/

          {model-id}/
            test-history.json
            latest-results.md

          prompt-strategies.md

        workflows/

        observations/
          training-patterns.md
        index.json
```

### Principles

1. `content/system/docs/` is shipped with the application and version-controlled in git
2. `content/user/docs/` is generated by the user's sessions and is local to each installation
3. Every directory contains an `index.json` for machine discovery
4. Markdown files use YAML frontmatter for structured metadata
5. Agents read `index.json` files; humans read `.md` files -- same data, two views

## Pipeline 1: Metrics (Deterministic)

### Trigger

Automatic at session completion, via existing `write-metrics` and `shell-format-report` workflow nodes.

### Process

1. Session completes
2. Script extracts `_phaseMetrics`, `_phases`, `_llmActivity` from session variables
3. Formats into structured files (JSON for machines, Markdown for humans via `format-metrics-report.js`)
4. Writes to `content/user/docs/metrics/`
5. Updates `content/user/docs/metrics/index.json`

### No LLM involved

The metrics pipeline NEVER uses an LLM. It extracts, formats, and stores. If it references a number, that number comes directly from session data.

## Pipeline 2: Knowledge (LLM-Powered)

### Trigger

- **Manual**: `maestro docs generate --knowledge` (user decides when to synthesize)
- **Periodic**: After N sessions completed (configurable)
- **Triggered**: After a session whose results contradict an existing knowledge article

Pipeline 2 is never automatic without an explicit signal. The user controls when synthesis happens.

### Process

1. Collect sources: read `content/user/docs/metrics/` (Pipeline 1 output) and existing knowledge articles
2. Analyze patterns (LLM): identify cross-session observations, confirmations, contradictions
3. Confront existing knowledge (LLM): update confidence levels, mark contradictions
4. Write/update articles (LLM): structured Markdown with YAML frontmatter
5. Clean up (LLM): merge redundant articles, deprecate obsolete ones
6. Update `content/user/docs/knowledge/index.json`

### Guards

| Risk | Guard |
|------|-------|
| Hallucinated metrics | The LLM never generates numbers -- it references Pipeline 1 metrics only |
| Data loss | Pipeline 2 never modifies `metrics/` (Pipeline 1). It only writes to `knowledge/` |
| False observations | Every article has `confidence` and `sources` fields for verification |
| LLM provider down | Pipeline 2 fails visibly (node status `error`). Pipeline 1 is unaffected |

## Model Documentation Format

Used in both `content/system/docs/models/` and `content/user/docs/models/`.

### Structure: YAML frontmatter + Markdown body

```markdown
---
modelId: "HuggingFaceTB/SmolLM2-1.7B-Instruct"
displayName: "SmolLM2 1.7B Instruct"
category: "instruction-following"
parameters: "1.7B"
quantization: null
requirements:
  vram: "~4GB"
  ram: "~8GB"
  gpu: "optional (CPU viable but slow)"
  os: ["windows", "linux", "macos"]
bestFor: ["json-generation", "structured-output", "instruction-following"]
avoidFor: ["code-generation", "long-form-text"]
fitnessRange: [0.85, 0.95]
lastTested: "2026-02-10"
testedBy: "compliance-tester"
---

# SmolLM2 1.7B Instruct

## Overview

[Description, provenance, license]

## Capabilities

| Task | Fitness | Notes |
|------|---------|-------|
| JSON structured output | 0.95 | Excellent -- best small model for this |
| Instruction following | 0.85 | Good with specific prompts |
| Code generation | 0.40 | Not recommended |

## Recommended Configuration

- Temperature: 0.3 (creation), 0.5 (optimization)
- Max tokens: 512-1024
- System prompt: Include explicit JSON schema

## Known Issues

- Adds trailing whitespace after JSON in ~5% of cases
- Temperature > 0.7 degrades JSON validity significantly

## Test History

| Date | Session | Fitness | Pass |
|------|---------|---------|------|
| 2026-02-10 | compliance-run-001 | 0.95 | Yes |
```

### Frontmatter fields

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `modelId` | string | Yes | Full model identifier |
| `displayName` | string | Yes | Human-readable name |
| `category` | string | Yes | Primary category (e.g. `instruction-following`, `code-generation`) |
| `parameters` | string | Yes | Parameter count (e.g. `"1.7B"`, `"7B"`) |
| `quantization` | string or null | Yes | Quantization level if applicable (e.g. `"Q4_K_M"`, `null`) |
| `requirements` | object | Yes | Hardware requirements: `vram`, `ram`, `gpu`, `os` |
| `bestFor` | string[] | Yes | Task types where the model excels |
| `avoidFor` | string[] | Yes | Task types where the model performs poorly |
| `fitnessRange` | number[] | Yes | [min, max] observed fitness scores |
| `lastTested` | string | Yes | ISO date of last test |
| `testedBy` | string | Yes | Session type that produced the results |

## Knowledge Article Format

Used in `content/user/docs/knowledge/`.

### Structure: YAML frontmatter + Markdown body

```markdown
---
topic: "prompt-strategies"
category: "models"
title: "Prompt Strategies for Small LLMs"
confidence: "high"
status: "validated"
sources:
  - sessionId: "experiment-001"
    date: "2026-02-08"
    relevance: "primary"
  - sessionId: "experiment-003"
    date: "2026-02-09"
    relevance: "confirming"
  - sessionId: "experiment-008"
    date: "2026-02-10"
    relevance: "confirming"
contradictions: []
lastUpdated: "2026-02-10"
updatedBy: "knowledge-pipeline-v1"
supersedes: []
relatedArticles:
  - "temperature-guide"
  - "model-selection-matrix"
---

# Prompt Strategies for Small LLMs

## Key Observation

[Core finding in 1-2 sentences]

## Evidence

[Data tables referencing Pipeline 1 metrics, never fabricated numbers]

## Recommendation

[Actionable guidance based on the evidence]

## Limitations

[Scope of testing, what has not been verified]

## History

[Chronological record of when the observation was made and confirmed]
```

### Frontmatter fields

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `topic` | string | Yes | Unique identifier for the article (used as filename) |
| `category` | string | Yes | Category: `models`, `workflows`, `observations`, `best-practices` |
| `title` | string | Yes | Human-readable title |
| `confidence` | string | Yes | One of: `high`, `medium`, `low`, `under-review`, `deprecated` |
| `status` | string | Yes | `validated`, `draft`, `under-review`, `deprecated` |
| `sources` | object[] | Yes | List of session references: `{ sessionId, date, relevance }` |
| `contradictions` | object[] | Yes | Articles or sessions that contradict this article (empty if none) |
| `lastUpdated` | string | Yes | ISO date of last modification |
| `updatedBy` | string | Yes | Who or what updated this article |
| `supersedes` | string[] | Yes | Topic IDs of articles this one replaces |
| `relatedArticles` | string[] | Yes | Topic IDs of related articles |

### Source relevance values

| Value | Meaning |
|-------|---------|
| `primary` | The session that first produced this observation |
| `confirming` | A session that independently confirmed the observation |
| `contradicting` | A session whose results conflict with the observation |

---

## Confidence Levels

| Level | Criteria | Display | Action |
|-------|----------|---------|--------|
| `high` | 3+ concordant sessions, 0 active contradictions | Reliable, actionable | Use in recommendations |
| `medium` | 1-2 sessions, or partially concordant results | Probably true, needs confirmation | Present with caveat |
| `low` | Single session, or preliminary observation | Hypothesis, needs more data | Flag as unverified |
| `under-review` | Contradictory data detected | Being re-evaluated | Do not use for decisions until resolved |
| `deprecated` | Superseded by newer data or confirmed obsolete | Historical only | Keep for reference, do not surface in recommendations |

### Confidence lifecycle

```
New observation
      |
      v
  [low confidence]
      |
      +-- Confirmed by 1-2 sessions --> [medium]
      |                                    |
      |                                    +-- Confirmed by 3+ sessions --> [high]
      |                                    |                                  |
      |                                    |                                  +-- Normal life
      |                                    |                                  |
      |                                    |                                  +-- Contradicted --> [under-review]
      |                                    |                                                         |
      |                                    +-- Contradicted --> [under-review]                       |
      |                                                            |                                 |
      +-- Contradicted immediately --> removed                     +-- Resolved --> back to level
                                                                   |
                                                                   +-- Confirmed obsolete --> [deprecated]
```

## CLI Commands

```
maestro docs list                        List all docs (metrics + knowledge summary)
maestro docs list --metrics              List metrics entries only
maestro docs list --knowledge            List knowledge articles only
maestro docs list --category models      Filter by category

maestro docs show <topic>                Display a doc (renders Markdown in terminal)
maestro docs show <topic> --json         Output as JSON (frontmatter fields, for agents)
maestro docs show <topic> --full         Full Markdown output

maestro docs generate --metrics          Run Pipeline 1 (deterministic extraction)
maestro docs generate --knowledge        Run Pipeline 2 (LLM synthesis)

maestro docs search <query>              Search across all documentation
```

---

## Rules

1. Pipeline 1 (metrics) NEVER uses an LLM. Data is extracted and formatted deterministically
2. Pipeline 2 (knowledge) reads Pipeline 1 output as source material. Pipeline 1 never reads Pipeline 2
3. Every knowledge article MUST have `sources` referencing real session IDs -- no unsourced claims
4. Knowledge articles that cite numbers MUST reference the Pipeline 1 metric file where the number originates
5. The `index.json` files are generated by scripts, not by LLMs
6. If the LLM provider is down, Pipeline 2 fails visibly (error status). Pipeline 1 is unaffected. No fallback content
7. YAML frontmatter fields are the contract between human-readable docs and machine-readable indexes
8. `content/system/docs/` is shipped with the app; `content/user/docs/` is generated per-installation
9. All documentation features in Phase 14 are CLI + TUI Monitor only -- no frontend React changes

Avant, le llm provider avait un monitor très bien. Maintenant, provider est un panel dans maestro code. Il manque des 
  fonctionnalitée critique pour la première version déployable. Le but de l'app est que ce soit facile de voir quel sont les capacités de mon ordinateur, quel modèle sont disponible. Le provider local devrait toujours être setupé. Le but est que la première fois que l'utilisateur arrive dans l'app, dans le setup, que ça lui montre les capacités de son ordinateur et lui demander quel modele (dans ceux qui sont disponibles) l'utilisateur voudrait downloader pour qu'il soit disponible dans maestro. le monitor LLM-Provider avait été développé quand LLM-Provider était encore séparé. Nous avions fait le choix de mettre provider directement dans maestro code mais il manque beaucoup de fonctionnalité qu'il avait avant. L'utilisateur ne peut pas de maestro code d'installer un modèle local au provider. Dans le monitor, il y avait plein de métriques et de panel intéressante pour l'utilisateur. Le but de cette phase est de faire en sorte que l'utilisateur ne tombe jamais dans l'application avec aucun provider et donc qui ne puisse pas tester l'app. Les tâches d'optimisation de faire une agent full qualité et de descendre tranquillement quand un plateau était atteinte est oui pour l'optimisation mais surtout pour permettre aux utilisateurs de toujours avoir une version qui fonctionne pour leur ordinateur. Je m'attends donc qu'à la fin de cette phase, un utilisateur arrive pour la première fois sur l'app et que dans le setting ça lui montre les capacités de son ordinateur, lui demande quel maestro-assistant l'utilisateur peut se permettre et lequel il veut "télécharger" tout de suite, qu'ensuite qu'il aille une autre demande de quel autre modèle local il vaut télécharger (il pourrait vouloir les télécharger même si ils ne veut pas le maestro-assistant qui utilise le modèle). Pour un utilisateur qui a vraiment pas de capacité, il se peut que le maestro-assistant ne soit pas capable de faire des réponses structurés. Il faut donc s'assurer que la logique actuelle de capacité qui je crois avait déjà été fait pour les blocks soit solide pour qu'il soit clair que pour "maestro-assistant", un block qui a les plusieurs fonctionnalités, que ça soit clair quel fonctionnalité est disponible et non disponible selon l'agent choisi. Ceci nécessite une analyse profonde des buts et phases antérieur que nous avions déjà parlé de cette fonctionnalité là. Il faut donc faire en sorte d'une certaine façon de faire un genre de model d'agent avec des tests qui spécifie les capacités nécessaire pour par exemple, faire la conversation avec l'utilisateur, des réponses structurés pour appeler les tools maestro, etc. Pour qu'un maestro-assistant créé par l'utilisateur ou tout simplement ou les différentes versions des maestro-assistant puisse afficher clairement les fonctionnalités qui vont être disponibles. Pour un utilisateur avec des modèles locaux très petit, ça devrait être clair pour lui que Ah, cette version de maestro assistant peut faire la fonctionnalité de converser mais pas d'appeler des tools. Ça va aussi permettre d'implémenter la feature adapt qui vient chercher les modèles que l'utilisateur a et adapter par tests automatisé (déjà parlé dans une autre phase) comment il peut adapter. (Nous allons mettre la fonctionnalité cloud plus tard). 

  Je m'attends aussi que nous aillons fait en sorte que ce qui était intéressant dans le monitor du llm-provider que soit qu'on adapte maestro-code pour que ce soit centralisé et que ce soit aussi intéressant qu'avant ou qu'on garde ça dans le monitor. Mais ça doit être clair pour l'utilisateur.

# 53-C : Blocks atomiques + migration handlers natifs

**Effort** : 2 jours
**Prerequis** : 53-B COMPLETE

---

## ERREURS INTERDITES

> **Lire AVANT de coder. Violation = revert immediat.**

1. **NE PAS re-implementer la logique de parsing de zero.** Le `response-parser` DOIT reprendre le code existant de l'ancien `AgentBlockExecutor` (extraction JSON, detection step-complete, multi-tool, trailing text). Ce code a ete debugge sur des dizaines de cas reels.

2. **NE PAS mettre de logique de conversation dans InferenceBlockExecutor.** L'inference block recoit `messages[]` et appelle le LLM. Point. Pas de `IConversationManager`, pas de system prompt loading.

3. **NE PAS creer de if-chain.** Chaque block a son propre executor ou est compose de nodes dans config.nodes. Pas de `if (toolType == "xxx")`.

4. **NE PAS creer de registre supplementaire.** `BlockExecutorRegistry` est le seul registre. Les blocks sont discovers par `IBlockDiscoveryService` et dispatches par le registry.

---

## Principe fondamental

> **La logique existante en C# est la REFERENCE.** Chaque block reproduit exactement la meme logique que le code C# faisait avant. On ne change pas le comportement — on le decoupe en blocks atomiques. C'est ce qui permettra la "compilation" : compresser les blocks en code natif pour zero overhead.

## Partie 1 : Blocks atomiques (nouveaux)

### 1.1 Block `response-parser`

Parse une reponse LLM brute et retourne un objet structure. **Reprend TOUTE la logique de l'ancien AgentBlockExecutor.**

```json
{
  "id": "response-parser",
  "blockType": "tool",
  "config": {
    "nodes": [
      { "id": "parse", "type": "native", "handler": "response-parser" }
    ]
  },
  "inputs": [
    { "name": "rawResponse", "type": "string", "required": true }
  ],
  "outputs": [
    { "name": "type", "type": "string" },
    { "name": "toolId", "type": "string" },
    { "name": "args", "type": "object" },
    { "name": "text", "type": "string" },
    { "name": "summary", "type": "string" }
  ]
}
```

**Logique extraite de l'ancien code** :
- `LLMBlockExecutorBase.ExtractJson()` — extraction JSON de la reponse
- Detection `step-complete` (anciennes lignes 430-516)
- Multi-tool detection (anciennes lignes 536-560)
- Trailing text capture (anciennes lignes 474-508)
- Empty response detection → type = "retry"
- Non-JSON response → type = "text" ou "retry"

**Output types** :
- `tool-call` : toolId + args extraits du JSON
- `step-complete` : summary extraite
- `text` : reponse textuelle (pas de tool call)
- `retry` : reponse vide ou malformee

**Executor** : `ResponseParserBlockExecutor : IBlockExecutor` — enregistre dans `BlockExecutorRegistry` comme handler pour ce block specifique, OU le tool block.json a un seul node `native` qui delegue a une methode dediee.

### 1.2 Block `tool-dispatcher`

Resout un tool par ID et l'execute via `BlockExecutorRegistry`.

```json
{
  "id": "tool-dispatcher",
  "blockType": "tool",
  "config": {
    "nodes": [
      { "id": "dispatch", "type": "native", "handler": "tool-dispatch" }
    ]
  },
  "inputs": [
    { "name": "toolId", "type": "string", "required": true },
    { "name": "args", "type": "object", "required": true }
  ],
  "outputs": [
    { "name": "result", "type": "string" },
    { "name": "success", "type": "boolean" },
    { "name": "toolOutputs", "type": "object" }
  ]
}
```

**Logique extraite** :
- `NormalizeToolId()` — normalisation des alias (bash→shell-execute, etc.)
- `ExecuteViaBlockDispatchAsync()` — resolution block, execution, formatage
- `_toolMapping` support — si le contexte contient un mapping, utiliser le block mappe

**DI** : Recoit `IBlockDiscoveryService` et `BlockExecutorRegistry`. Pas de circularite car c'est un tool block.

## Note sur `type: "native"`

Les blocks atomiques ci-dessus utilisent `"type": "native"` dans leurs nodes. C'est un type de node special qui execute du code C# enregistre par DI. La difference avec l'ancienne approche :

- **Avant** : handler inline dans un god class (`if (toolType == "xxx")`)
- **Apres** : handler C# enregistre par DI, reference par un block.json avec `config.nodes`

Le block.json definit le schema (inputs/outputs). Le handler C# fait le travail. `NodeExecutionEngine` dispatch via `BlockExecutorRegistry`. Pas de if-chain.

A terme, les handlers natifs les plus simples pourront etre remplaces par des blocks composes de nodes — mais pour la migration initiale, on garde la logique C# existante.

## Design

### test-harness.ts
- `startTestBackend()` : demarre le sidecar avec `skipLlm: true`, auto-port
- `stopTestBackend()` : arrete le sidecar
- `getClient()` : retourne un `MaestroClient` connecte au backend de test
- `importTemplate(client, sessionId, templateName)` : lit le JSON template, set les variables et entry points via SDK

### poll.ts
- `pollUntil(fn, options)` : appelle `fn()` toutes les `intervalMs` jusqu'a ce qu'elle retourne `true` ou timeout
- `waitForWorkflowComplete(client, sessionId, timeoutMs)` : poll `_activeWorkflow === ""`

### setup.ts (globalSetup)
- vitest `globalSetup` : demarre le sidecar une fois pour toute la suite
- Le port est passe via `process.env.TEST_BACKEND_URL`
- `teardown` arrete le sidecar

### health.test.ts
- `GET /` ou endpoint health du backend
- Verifie status healthy

## Verification

```bash
cd packages/maestro-integration-tests && npx vitest run tests/level-1-api/health.test.ts
# Attendu : sidecar demarre, health check passe, sidecar s'arrete
```

## Anti-patterns

- Ne PAS demarrer un sidecar par test — un seul pour toute la suite
- Ne PAS hardcoder le port — utiliser auto-port du sidecar
- Ne PAS utiliser require() — tout en ESM

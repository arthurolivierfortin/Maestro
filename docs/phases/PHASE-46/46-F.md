# 46-F : Test end-to-end du flux premier lancement

**Effort estime** : 2h

---

## Lecture obligatoire

- `packages/maestro-code/tests/App.test.ts` — pattern de test ink-testing-library (render, lastFrame, stripAnsi, delay)
- `packages/maestro-code/components/ProviderSetupScreen.ts` — comprendre le flux de selection provider (phases, touches, navigation)
- `packages/maestro-code/App.ts` — flux `handleProviderSetupComplete`, creation du SessionManager apres setup
- `packages/maestro-code/services/SessionManager.ts` — `ensureSession`, `submitTask`

---

## Ce que cette sous-phase fait

1. **Creer `tests/first-run.test.ts`** — tests d'integration du flux premier lancement avec ink-testing-library (pas PTY) :

   **Scenario 1 : Provider setup → session creee avec importSessionTemplate**
   - Rendre App avec `hasProviders: false`, mock `ensureBackendFn` (retourne un mock apiClient), mock `saveProviders`
   - Verifier que ProviderSetupScreen s'affiche (texte "Select your LLM provider" ou similaire)
   - Simuler la selection d'un provider (touches clavier)
   - Simuler la confirmation
   - Verifier que `ensureBackendFn` est appele
   - Verifier que l'agent page s'affiche (texte "CONVERSATION" ou "AGENT STATUS")
   - **Verifier que le SessionManager cree possede `importSessionTemplate`** — c'est le test du bug corrige en 46-A

   **Scenario 2 : Skip setup → TUI accessible sans backend**
   - Rendre App avec `hasProviders: false`
   - Simuler le skip du provider setup (touche Escape ou equivalent)
   - Verifier que l'agent page s'affiche meme sans backend

   **Scenario 3 : Providers deja configures → pas de setup screen**
   - Rendre App avec `hasProviders: true`, mock apiClient
   - Verifier que ProviderSetupScreen ne s'affiche PAS
   - Verifier que l'agent page s'affiche directement

   **Scenario 4 : Premier message apres setup invoque importSessionTemplate**
   - Apres le setup, verifier que soumettre un message appelle `importSessionTemplate` (pas le noop)
   - Cela garantit que le fix de 46-A fonctionne end-to-end

2. **Ajouter `first-run.test.ts` au script `test:fast`** dans package.json

## Pattern de test

```typescript
import { describe, it, expect, vi, afterEach } from 'vitest';
import { createElement as h } from 'react';
import { render, cleanup } from 'ink-testing-library';

// Mock ensureBackendFn
const mockImportTemplate = vi.fn().mockResolvedValue(undefined);
const mockApiClient = {
  createSession: vi.fn().mockResolvedValue({ id: 'sess-test' }),
  startSession: vi.fn().mockResolvedValue({}),
  getSession: vi.fn().mockResolvedValue({ status: 'idle', variables: {} }),
  _fetch: vi.fn().mockResolvedValue({}),
  // ... IApiClient stubs
};

const mockEnsureBackend = vi.fn().mockResolvedValue({
  apiClient: mockApiClient,
  sidecar: null,
});

// Render App in first-run mode
const { lastFrame, stdin } = render(h(App, {
  apiClient: null,
  sessionManager: null,
  hasProviders: false,
  ensureBackendFn: mockEnsureBackend,
  importSessionTemplate: mockImportTemplate,
  saveProviders: vi.fn(),
  readProviders: () => null,
}));
```

## Anti-patterns

- Ne PAS tester avec un vrai backend — ink-testing-library + mocks suffit
- Ne PAS utiliser PTY pour ce test — c'est un test logique, pas visuel
- Ne PAS tester le contenu exact des ecrans (fragile) — tester la presence d'elements cles et le flux de navigation
- Ne PAS mocker React — mocker seulement l'API client et les callbacks

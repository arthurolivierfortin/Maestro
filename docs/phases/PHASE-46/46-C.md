# 46-C : Typage TypeScript — fichiers critiques

**Effort estime** : 4h

- `packages/maestro-code/mocks/DemoApiClient.ts` — implemente les methodes extra hors IApiClient (createSession, startSession, _fetch)

## Ce que cette sous-phase fait

1. **Creer `packages/maestro-code/types.ts`** — types centralises :

   ```typescript
   import type { IApiClient } from '@maestro/tui/types';

   export interface IMaestroCodeApiClient extends IApiClient {
     createSession(opts: CreateSessionOptions): Promise<{ id: string }>;
     startSession(id: string): Promise<unknown>;
     _fetch(method: string, path: string, options?: { body?: unknown }): Promise<unknown>;
   }

   export interface CreateSessionOptions {
     repositoryPath: string;
     authority: string;
     name: string;
   }

   export interface InteractiveOptions {
     apiClient?: IMaestroCodeApiClient | null;
     sidecar?: { stop(): Promise<void> } | null;
     repoPath?: string;
     template?: string;
     entryPoint?: string;
     importSessionTemplate?: (sessionId: string, templateName: string, options?: { quiet?: boolean }) => Promise<void>;
     noSplash?: boolean;
     isFirstRun?: boolean;
     hasProviders?: boolean;
     ensureBackendFn?: () => Promise<{ apiClient: IMaestroCodeApiClient; sidecar: any }>;
     saveProviders?: (providers: Record<string, any>) => void;
     readProviders?: () => Record<string, any> | null;
     demo?: boolean;
     noBell?: boolean;
   }
   ```

   Cela elimine les 2 copies d'`InteractiveOptions` (launcher.ts et SessionManager.ts) et les nombreux `(options as any)` casts.

   **Decision de design** : creer `IMaestroCodeApiClient` dans maestro-code plutot que modifier `IApiClient` dans `@maestro/tui`. Raison : `_fetch` est un detail d'implementation de `MaestroApiClient`, pas un contrat universel. Les ecrans de monitoring n'en ont pas besoin.

2. **Typer `SessionManager.ts`** :
   - Supprimer `// @ts-nocheck`
   - Importer `IMaestroCodeApiClient`, `InteractiveOptions` depuis `./types.ts`
   - Remplacer `private client: any` par `private client: IMaestroCodeApiClient`
   - Supprimer l'export local de `InteractiveOptions` (utiliser celui de types.ts)
   - Garder les exports de `LogLine` et `Widget` dans SessionManager.ts (ou les deplacer vers types.ts si ca simplifie)
   - Typer toutes les methodes publiques et privees

3. **Typer `App.ts`** :
   - Supprimer `// @ts-nocheck`
   - Importer `InteractiveOptions`, `IMaestroCodeApiClient` depuis `./types.ts`
   - Typer les props de App avec une interface nommee `AppProps`
   - Corriger les `(options as any)` dans `startInteractive` avec les vrais types
   - Note : les sous-composants internes (`FullscreenBox`, `WidgetRenderer`, `NoBackendScreen`) peuvent garder du typage minimal dans cette sous-phase — ils seront traites en 46-D

4. **Typer `launcher.ts`** :
   - Supprimer `// @ts-nocheck`
   - Supprimer l'interface `InteractiveOptions` locale
   - Importer `InteractiveOptions` depuis `./types.ts`

5. **Typer `DemoApiClient.ts`** :
   - Supprimer `// @ts-nocheck`
   - Implementer `IMaestroCodeApiClient` explicitement

6. **Activer `noImplicitAny: true` dans `tsconfig.json`** :
   - C'est le reglage qui aurait attrape le bug du provider setup
   - Ne PAS activer `strict: true` complet — `noImplicitAny` est le plus utile sans casser les fichiers non-encore-types (ceux avec @ts-nocheck ne sont pas affectes de toute facon)

## Anti-patterns

- Ne PAS ajouter `_fetch` a l'interface `IApiClient` de `@maestro/tui` — c'est un detail d'implementation, pas un contrat universel
- Ne PAS essayer de typer tous les fichiers dans cette sous-phase — 46-C = fichiers critiques seulement, 46-D = composants
- Ne PAS remplacer `strict: false` par `strict: true` d'un coup — `noImplicitAny: true` suffit
- Ne PAS refactoriser la logique en typant — uniquement ajouter les annotations de type
- Ne PAS creer de fichiers `.d.ts` separes — les types inline dans `.ts` sont preferables
